# FLOODLENS-AI — Implementation Plan

Deadline-driven plan for Multimodal AI Hackathon 2026, Track B. Prioritize a small, validated end-to-end workflow over breadth.

## M1 — Acquire imagery and produce a real flood mask
- Select a documented pretrained flood-segmentation baseline and confirm its license, checkpoint, architecture, required input bands, preprocessing, and inference protocol.
- Obtain a compatible georeferenced Sentinel-1 scene and preserve its spatial metadata.
- Run a minimal inference smoke test and save a mask plus diagnostic overlay.
- **Acceptance:** mask is generated by the model from compatible data, outputs vary spatially, and the exact scene/model/preprocessing are recorded. No mock or color-thresholded satellite screenshot presented as AI inference.

## M2 — Validate prediction and geospatial alignment
- Verify raster dimensions, CRS, transform, nodata handling, and mask alignment.
- Use matching independent reference labels where available.
- Calculate appropriate metrics such as IoU, precision, and recall; document thresholds and limitations.
- **Acceptance:** reproducible validation output and a georeferenced mask that aligns with the source raster.

## M3 — Build the FastAPI inference interface
- Expose a small inference endpoint using the verified pipeline.
- Validate upload type, size, band count, dimensions, and error responses.
- Keep large data and model weights outside Git; use configuration/environment variables where appropriate.
- **Acceptance:** documented endpoint can process a supported input and return mask metadata/results with tests.

## M4 — Build the interactive dashboard
- Use React, TypeScript, and Leaflet for a polished map-first command center.
- Display image/context layers, flood mask, confidence/threshold information, and an evidence panel.
- Clearly distinguish observed outputs, external context, derived inferences, and unavailable information.
- **Acceptance:** a user can load the demo scene and inspect a correctly aligned result end to end.

## M5 — Add road-network connectivity and impact analysis
- Integrate a documented road-network source for the demo area.
- Implement transparent graph analysis to identify roads/settlements potentially affected by intersecting flood evidence.
- Label findings as estimates; disclose data freshness, assumptions, and uncertainty. Do not claim confirmed bridge damage, people trapped, or communications failure without evidence.
- **Acceptance:** at least one reproducible connectivity example with inspectable evidence and an honest explanation of assumptions.

## M6 — Test, deploy, and prepare submission
- Run smoke tests on the whole workflow and resolve critical UI/API errors.
- Deploy to a public host and verify it from a fresh browser session.
- Prepare a short demo showing inputs, real inference, spatial result, and connectivity reasoning.
- Complete README, architecture/data provenance, model/dataset attribution and license notes, known limitations, and AI-assistant disclosure.
- **Acceptance:** public demo URL works; project can be explained and reproduced; no unsupported accuracy or impact claims.

## Execution rules
- Complete and verify one milestone before expanding scope.
- Do not commit datasets, checkpoints, secrets, or generated bulk artifacts.
- Prefer pretrained inference over training from scratch given the deadline.
- If the selected model/data path is blocked, switch to a verified fallback quickly and document the change.
